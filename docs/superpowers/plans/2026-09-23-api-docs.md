# API 문서화 도입 (Step 15) Implementation Plan

> **이 레포의 실행 규칙 (skill 기본형과 다름):**
> **코드는 사용자가 직접 작성한다.** 이 플랜은 *무엇을·어디에·왜* 와 목표 형태·검증 방법만 담고,
> 완성된 구현 코드를 싣지 않는다 (`CLAUDE.md` — 학습이 목적). 각 Task 의 "목표 형태" 는
> 시그니처·스키마 수준이며, 본문 로직은 사용자가 쓴다. Claude 는 힌트·리뷰만 한다.
> 서브에이전트에 위임하지 않는다.

**Goal:** curl 대신 브라우저에서 Cats API 를 읽고 호출할 수 있게 하되, 문서가 **실제 응답 봉투와 일치**하게 만든다.

**Architecture:** `@nestjs/swagger` 가 컨트롤러·DTO 메타데이터로 OpenAPI 문서를 만들고, Swagger UI(`/api`)와
Scalar(`/reference`)가 같은 문서를 렌더링한다. 전역 인터셉터·필터가 씌우는 `{data}`/`{error}` 봉투는
Swagger 가 모르므로 **응답 데코레이터로 명시**한다 — 처음엔 손으로, 반복이 보이면 커스텀 데코레이터로.

**Tech Stack:** NestJS 12.0.1 / `@nestjs/swagger` 12.0.1 / `@scalar/nestjs-api-reference` 1.2.21 / Express 5 / class-validator

**Spec:** 이 문서의 `## 확정 사항` 절 (2026-09-23 grilling 세션에서 확정)

### ⚠️ grilling 에서 빠졌던 결정 — `Cat` 이 interface 라 스키마가 안 나온다

`getSchemaPath(Cat)` · `@ApiProperty` 는 **런타임 클래스**가 있어야 동작한다. `Cat` 은 `interface` 라
컴파일 후 사라진다 → 문서에 넣을 대상 자체가 없다. 확정 전제 "외부 입력(DTO) = class, 내부 타입 =
interface" 와 부딪힌다.

| 안 | 내용 | 비용 |
|---|---|---|
| **A (추천)** | `Cat` 을 class 로 바꿔 `src/cats/entities/cat.entity.ts` 로 옮긴다. 경계를 **"런타임 메타데이터가 필요한 타입 = class"** 로 다시 긋는다 | import 경로 변경 (service·controller·spec) |
| B | `interface Cat` 유지 + 응답 전용 `CatResponseDto` class 를 따로 만든다 | 필드 4개 이중 서술 — Step 10 에서 없앤 종류의 중복 |

**A 추천 이유:** `.entity.ts` 는 CLI plugin 의 기본 인식 대상이라 Task 7 에서 수동 `@ApiProperty`
가 그대로 지워진다(기본값은 Task 7 Step 1 에서 문서로 확인). B 는 응답과 내부 타입이 따로 놀 수 있는
SSOT 둘을 만든다. **플랜 리뷰 때 A/B 를 확정해 준다.** 아래 Task 는 A 기준이다.

### 요약에서 정정 — `allOf` 는 이번 봉투엔 필요 없다

공식 예제의 `allOf` 는 `PaginatedDto` 라는 **베이스 스키마에 필드를 덧붙일 때** 쓴다. `{data: T}` 는
베이스가 없는 단일 프로퍼티라 `properties.data.$ref` 만으로 표현된다. `getSchemaPath` + `ApiExtraModels`
는 그대로 필요하다. 에러 봉투까지 공통 베이스로 묶고 싶어지면 그때 `allOf` 가 등장한다.

## Global Constraints

- NestJS **12.0.1**, `@nestjs/swagger` **12.0.1** (`@nestjs/core` 와 메이저 일치) — API 확인은 `docs.nestjs.com/v12/`

스펙이 함의하지만 어느 Task 의 기본 검증도 직접 다루지 않는 입력들. 각 줄은 담당 Task 에 검증 항목으로 넣었다.

2. **`UpdateCatDto` 스키마가 비어 나온다** → `PartialType` 을 `@nestjs/mapped-types` 에서 가져오면

## Task 3: 성공 봉투를 손으로 문서화 (`GET /cats/:id` 한 곳)

**Files:**
- Modify: `src/cats/cats.controller.ts`

**Interfaces:**
- Consumes: `Cat` (Task 2)
- Produces: 없음 — Task 4 가 이 손 버전을 데코레이터로 옮긴다

**목표 스키마** (`/api-json` 에서 `GET /cats/{id}` 의 200 응답):
```json
{
  "type": "object",
  "properties": { "data": { "$ref": "#/components/schemas/Cat" } }
}
```

- [ ] **Step 1: 대조군**

```bash
curl -s http://localhost:3000/api-json | jq '.paths["/cats/{id}"].get.responses'
```
기대: `{"200":{"description":""}}` 정도 — 스키마 없음. **반환 타입 추론이 안 되는 이유**를 생각해 둔다
(`findOne` 은 반환 타입 표기가 없고, 있어도 봉투는 인터셉터가 씌운다).

- [ ] **Step 2: `findOne` 에 두 데코레이터**

- 메서드(또는 클래스)에 `@ApiExtraModels(Cat)` — `Cat` 을 `components.schemas` 에 **등록**
- `@ApiOkResponse({ schema: … })` — 위 목표 스키마. `$ref` 값은 `getSchemaPath(Cat)` 로 얻는다

> **왜 `ApiExtraModels` 가 필요한가:** `getSchemaPath` 는 `"#/components/schemas/Cat"` **문자열만**
> 만든다. 그 경로에 실제 스키마를 넣는 건 별개다. 빼보면 `$ref` 가 존재하지 않는 곳을 가리키는
> 문서가 만들어진다 — 한 번 빼고 Step 3 을 돌려 확인해 볼 것.

- [ ] **Step 3: 검증**

```bash
curl -s http://localhost:3000/api-json | jq '.paths["/cats/{id}"].get.responses["200"].content["application/json"].schema'
curl -s http://localhost:3000/api-json | jq '.components.schemas.Cat.properties | keys'
```
