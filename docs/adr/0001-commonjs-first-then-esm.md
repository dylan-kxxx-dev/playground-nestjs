# 0001 — CommonJS로 학습 후 ESM 전환

## Status

Accepted

## Context

NestJS v12 `nest new`는 CommonJS / ESM 중 선택을 요구하며, 선택에 따라 툴체인이 갈린다:

| | CommonJS | ESM |
|---|---|---|
| 테스트 | Jest | Vitest |
| 린트 | ESLint | oxlint |

이 레포의 목적은 **NestJS 학습**이다(프로덕션 아님). 제약과 힘:

- ESM이 JS 표준이고 장기적으로 CommonJS를 대체한다 — 방향 자체는 논란 없음.
- 그러나 NestJS 학습 자료(문서 외 블로그·Stack Overflow)는 대부분 CommonJS 기준이다.
- 학습 중 막혔을 때 "NestJS를 몰라서"인지 "ESM 설정이 꼬여서"인지 구분하기 어렵다.
  원인 축이 둘이면 디버깅이 학습을 밀어낸다.
- 개인 플레이그라운드라 실패 비용이 0에 가깝다.

## Decision

**CommonJS로 먼저 학습하고, 그 뒤 ESM으로 전환한다.**

전환 방식(미러 프로젝트 신규 생성 vs 기존 프로젝트 마이그레이션)은 Phase 1 완료 시점에
정한다 — 지금 정할 근거가 부족하고, 미루는 비용이 없다.

## Consequences

**쉬워지는 것**
- 한 번에 한 가지만 배운다 — 모듈 시스템이 NestJS 학습을 방해하지 않는다.
- 검색 자료가 코드와 일치해 막힌 지점의 원인이 하나로 좁혀진다.
- 마이그레이션 자체가 2차 학습 소재가 된다. ESM 차이(`__dirname` 부재,
  상대경로 확장자 필수, top-level await)를 읽는 대신 실제로 깨뜨려보며 익힌다.

**어려워지는 것**
- 학습 내용 일부가 CommonJS 전제에 묶인다 — 전환 시 재작업이 생긴다.
- Jest → Vitest 전환 시 테스트 코드 수정 필요.

**후속 의무**
- Phase 1(Overview 9단계) 완료 시 전환 방식을 결정하고 ADR 0002로 기록한다.
- 전환 시점에 v12 ESM 문서를 다시 조회한다 — 기억이 아니라 문서 기준.

## Alternatives Considered

- **처음부터 ESM** — 표준이고 v12가 미는 방향이며 Vitest가 Jest보다 빠르다.
  기각 이유: 학습 초기에 원인 축이 둘로 늘어난다. 배우려는 대상은 NestJS이지
  모듈 시스템이 아니다. 단, 이 기각은 *학습 단계에 한정*이며 최종 목표는 ESM이다.
- **CommonJS만 쓰고 전환 안 함** — 가장 단순.
  기각 이유: 사양 방향과 어긋난다. 학습 레포에서 낡은 전제를 굳힐 이유가 없다.
